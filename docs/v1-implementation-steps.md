# RtPath 首版实现步骤

优先跑通普通权限下的搜索和落盘，再引入 Root 与实时更新。每个阶段都给出一个可独立验证的结果。性能口径见[首版验证](v1-validation.md)，外部实现和源码版本见[开源实现参考](open-source-references.md)。关键部分达到对应验收条件后，可以作为独立 Git 提交，提交说明记录已完成的范围和验证结果。

## 0. 初始化 Android 工程和能力探针

- 在现有仓库内创建仅 Android 的 Flutter 工程，设置应用 ID、构建配置和原生 CMake 入口。初始环境以 DiskSize 的已验证配置为基线，并用 Flutter 生成的工程验证 Gradle 兼容性。
- 目标为 Android 10+（`minSdk 29`），`compileSdk` / `targetSdk` 为 36，构建 `arm64-v8a` 和 `x86_64`。用本机路径配置当前终端或被 Git 忽略的本地配置。
- 构建可在普通应用进程运行的探针，验证现有 NDK、实际打包的 SQLite trigram 建表与样例查询、原生 inotify 和基础文件读取。在 Root 链路可运行后，用同样的受控样本验证文件系统的 fanotify 能力。

| 工具 | 本机位置和版本 |
| --- | --- |
| Flutter / Dart | `E:\Projects\.toolchains\flutter`，3.47.9 / 3.13.7 |
| Android SDK | `I:\Software\Android\SDK`，Platform 36，Build Tools 36.0.0 |
| Android NDK | `I:\Software\Android\SDK\ndk\28.2.13676358` |
| CMake | `I:\Software\Android\SDK\cmake\3.22.1` |
| JDK | `D:\Software Environment\jdk-21.0.9` |

**验收通过时**，Android Debug APK 能运行，C++ JNI 对应两个 ABI 能构建，探针能报告系统版本、SQLite 能力和普通模式可见范围。 本次结果见 [阶段 0 验证记录](phase0-baseline.md)。

## 1. 跑通普通扫描和索引闭环

- 参考 DiskSize 的 C++ 流式遍历、取消、挂载边界和错误处理。先用应用自有样本接通 JNI、Kotlin 服务和批量 SQLite 写入，再扩展到获授权的共享存储。
- 实现扫描范围、父目录关系、暂存写入和终态原子发布。查询结果绑定可用版本，验证重扫途中旧版本仍可读。暂存所需空间和取消回滚可参考 [Android Everything](open-source-references.md#android-everything)。
- 通过 Pigeon 暴露扫描、取消、状态和首个查询入口，做出最小 Flutter 搜索页。

**验收通过时**，普通模式可完成扫描、查询和重启后的索引读取。扫描取消后保留上次可用结果。真机结果和复现命令见[阶段 1 验证记录](phase1-baseline.md)。

## 2. 实现文件搜索和滚动体验

- 实现精确、前缀、字面子串、短字符回退，以及扩展名、目录范围和大小过滤。返回有确定排序和游标的结果页，显示名称、路径、大小及修改时间，并支持复制完整路径。
- 在 10 万条和 100 万条上对比 FTS5 与等价的内存过滤，单列中文一字、二字和低命中查询。结合查询计划验证常见过滤、字面子串及路径排序，按实测决定增加哪些索引。

**验收通过时**，中文、同名、组合过滤和百万条分页验证通过，生成第一轮性能报告。结果与复现方式见[阶段 2 搜索验证与性能](phase2-search.md)。

## 3. 接入显式 Root 扫描

- 增加 libsu RootService、Binder 控制、批量管道和断开处理。两种扫描模式共用 C++ 核心。Root 进程只负责元数据读取和事件生产，普通 UID 服务负责数据库。
- 验证实际挂载命名空间、目标路径可读性及退出场景。加入模式选择和覆盖状态。记录普通、Root 两个扫描入口的挂载视图。在实际 Root 进程运行 fanotify 能力探针，按文件系统记录结果。

**验收通过时**，已授权的 Root 服务可扫描选定测试范围，普通服务可独立完成查询和索引维护。Root 断开后界面状态和索引范围正确。

## 4. 实现 inotify 增量更新

- 实现目录 watch 生命周期、非阻塞事件读取、移动配对、范围校验和事件合并。把变更应用到普通服务的同一事务写入路径，再通知 Flutter 更新正在显示的查询。
- 将监听接入首次扫描和重建，处理枚举期事件及新建、移入目录的覆盖。按会话记录队列位置、目录 watch 注册、失败和恢复所需范围。普通及 Root 的监听分别跟随各自扫描器的权限和挂载视图，并跑共享存储正反向写入用例。

**验收通过时**，新建、删除、写入和目录改名在现场查询中更新。编辑器原子保存、移入整棵目录和并发扫描通过对账。普通文件事件只局部更新索引。

## 5. 做完恢复和设备验收

- 测试队列溢出、watch 上限、挂载变化、监听进程死亡、权限撤销、取消和空间不足。按可定位范围补扫，并验证事务发布、界面状态和重试。
- 在普通和 Root 真机复测首屏、增量刷新、建库、资源与 DB 体积。分别记录普通模式和 Root 模式的实际覆盖范围、失败原因、缺口修复时补扫的目录和条目数。

**验收通过时**，首版验收矩阵有运行记录，剩余限制明确。监控存在缺口时可查询历史结果，并能重建正确索引。

## 6. 在能力通过的 Root 范围启用 fanotify

- 复用相同的增量写入和恢复逻辑，实现文件系统级标记、FID/名称映射、目录移动、范围过滤和溢出恢复。以真实创建、删除、重命名事件决定是否启用。
- 对通过探针的文件系统和 inotify 后端运行同一套夹具，对比覆盖、事件端到端延迟和资源占用。首版可把已验证的 fanotify 范围作为可选能力交付，其他范围按 inotify 验收。

**验收通过时**，探针通过的范围完成对账并能恢复缺口。探针未通过的范围自动使用已验证的兼容后端。
